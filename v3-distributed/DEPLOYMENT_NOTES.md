# Deployment Notes - SITM-MIO V3 Distributed ICE

## Linux-Only Deployment

This deployment is intended for Linux computers. Windows scripts were removed from `v3-distributed`; use only the `.sh` scripts.

## Distributed Component Names for UML Deployment

Use domain-aligned names in the deployment diagram while keeping the technical pattern names in code.

| Distributed component in diagram | Architectural pattern / role | Implementation |
|---|---|---|
| AnalystClient | Client process that submits the speed calculation request | `client/ClientApp.java` |
| BusEventMonitor | Event-driven visualization of the distributed message bus | `visualization/VisualizationI.java` |
| SpeedCalculationBroker | Broker pattern, stable endpoint for clients | `broker/BrokerI.java` |
| SpeedCalculationMaster | Master role, worker registry, partition dispatch, reduction | `master/MasterI.java` |
| SpeedPartitionWorker | Worker role, stateless partition processor | `worker/WorkerI.java` |
| DatagramPartitioner | Pipe/filter preprocessing stage for large CSV partitioning | `partitioner/DatagramPartitionerApp.java` |
| PartitionedDatagramStore | Local partition files consumed by workers | `data/partitions-N/partition-X.csv` |
| SpeedResultsStore | Final output generated by Master | `output/resultados-v3.csv` |

Recommended UML label format:

```text
<<process>> SpeedCalculationBroker
implementation: broker/BrokerI.java
pattern: Broker
```

## Source Diagram Corrections

The provided `DeploymentFinal.pdf` shows high-level SITM-MIO devices but does not explicitly separate Broker, Master and Workers. The corrected deployment must show the following physical separation:

```text
AnalystClient -> SpeedCalculationBroker -> SpeedCalculationMaster -> SpeedPartitionWorker(s)
                                      BusEventMonitor <- events
```

## Corrected Flexible Deployment

Formula:

```text
Total computers = N workers + 2
```

Node allocation:

```text
Computer 1 - CCO Client Node
- AnalystClient JVM
- BusEventMonitor JVM
- BusEventMonitor endpoint: tcp -h <PC1_IP> -p 10003

Computer 2 - Analytics Coordination Node
- SpeedCalculationBroker JVM
- SpeedCalculationMaster JVM
- SpeedCalculationBroker endpoint: tcp -h <PC2_IP> -p 10000
- SpeedCalculationMaster endpoint: tcp -h <PC2_IP> -p 10001

Computer 3 - Analytics Worker Node 1
- SpeedPartitionWorker JVM
- Worker endpoint: tcp -h <PC3_IP> -p 10011
- Local data: data/partitions-N/partition-0.csv

Computer 4 - Analytics Worker Node 2
- SpeedPartitionWorker JVM
- Worker endpoint: tcp -h <PC4_IP> -p 10012
- Local data: data/partitions-N/partition-1.csv

Computer N+2 - Analytics Worker Node N
- SpeedPartitionWorker JVM
- Worker endpoint: tcp -h <PCN_IP> -p 10010+N
- Local data: data/partitions-N/partition-(N-1).csv
```

## Startup Order

```text
1. DatagramPartitioner, executed once before deployment
2. BusEventMonitor
3. SpeedPartitionWorkers 1..N
4. SpeedCalculationMaster
5. SpeedCalculationBroker
6. AnalystClient
```

Workers can start before Master because they retry self-registration through ICE.

## Linux Commands

Build:

```bash
./gradlew build
```

Prepartition for 8 workers:

```bash
bash v3-distributed/prepartition.sh 8
```

Small experiment:

```bash
bash v3-distributed/prepartition.sh 8 1000000
```

Start visualization on PC1:

```bash
bash v3-distributed/start-visualization.sh <PC1_IP>
```

Start each worker:

```bash
bash v3-distributed/start-worker.sh worker-1 10011 <MASTER_IP> <WORKER_1_IP>
bash v3-distributed/start-worker.sh worker-2 10012 <MASTER_IP> <WORKER_2_IP>
```

Start Master on PC2:

```bash
bash v3-distributed/start-master.sh <PC2_IP> <PC1_IP>
```

Start Broker on PC2:

```bash
bash v3-distributed/start-broker.sh <PC2_IP> <PC2_IP> <PC1_IP>
```

Run Client on PC1:

```bash
bash v3-distributed/start-client.sh <PC2_IP> 8 data/partitions-8
```

## Pattern Compliance

### Broker

`SpeedCalculationBroker` is the only endpoint known by `AnalystClient`. Client-to-worker communication is not allowed.

### Master-Worker

`SpeedCalculationMaster` owns the worker registry and dispatches partitions to registered `SpeedPartitionWorker` processes. Workers are stateless: they receive a task, process a partition and return partial statistics.

### Pipe-and-Filter

```text
DatagramPartitioner -> SpeedCalculationBroker -> SpeedCalculationMaster -> SpeedPartitionWorker -> SpeedCalculationMaster reducer -> SpeedResultsStore
```

### Event-Driven Visualization

`SpeedCalculationBroker` and `SpeedCalculationMaster` publish events to `BusEventMonitor` asynchronously. Visualization does not block ICE request processing.

## Anti-Patterns Avoided

- Client-to-worker calls that bypass Broker.
- Broker and Master merged in the same process role.
- Hardcoded proxies inside Java classes instead of `.cfg` files or startup script properties.
- Visualization work inside the ICE dispatch thread.
- Worker registry based on non-thread-safe collections.
- Every worker reading the full dataset during distributed execution.

## Middleware Choice

Manual ICE adapters are used instead of IceGrid.

Reason:

Manual endpoint configuration is enough for Linux lab machines and keeps every process independently launchable while still using ZeroC ICE for all inter-process communication.
